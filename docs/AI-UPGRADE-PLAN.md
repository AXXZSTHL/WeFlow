# WeFlow AI 升级方案草案

## 1. 升级目标

WeFlow 现在已经具备聊天浏览、聊天分析、人物画像、话题分析、AI 回复生成、年度报告、朋友圈与资源浏览等能力。下一阶段不建议只做一个孤立的“浓缩用户”按钮，而是把产品升级为一个更完整的 **个人关系 AI 工作台**。

核心目标有三个：

1. 把聊天记录从“可查看的数据”升级为“可复用的关系资产”。
2. 把一次性 AI 报告升级为可沉淀、可更新、可对话的联系人档案。
3. 把 AI 能力从“分析工具”升级为“理解人、辅助沟通、模拟互动、提醒决策”的产品系统。

## 2. 核心概念命名

### 2.1 “浓缩用户”的推荐命名

不建议最终按钮直接叫“浓缩用户”。这个词表达准确，但对普通用户略技术化，也不够有情绪价值。

推荐命名：

| 场景 | 推荐名称 | 说明 |
| --- | --- | --- |
| 聊天页右上角按钮 | 生成 AI 分身 | 最直观，用户能理解“生成一个可模拟对话的 TA” |
| 生成后的对象 | AI 分身 | 适合后续聊天入口 |
| 结构化资料 | 人格档案 | 适合展示分析结果、技能、偏好、说话方式 |
| 左侧菜单入口 | AI 分身库 | 直接表达“我已经生成了哪些人” |
| 备用菜单名 | 关系智能体 | 更专业，但略抽象 |
| 备用菜单名 | 人格档案库 | 更严肃，适合偏工具化定位 |

最终建议：

- 聊天页按钮：`生成 AI 分身`
- 左侧菜单：`AI 分身库`
- 列表页标题：`我的 AI 分身`
- 单个详情页：`TA 的人格档案`
- 对话页输入框提示：`和 TA 的 AI 分身聊聊...`

### 2.2 为什么不用“skills”直接面向用户

“skills”更适合作为内部数据结构名，不适合作为用户可见命名。用户真正关心的是：

- TA 是什么样的人
- TA 会怎么说话
- TA 在意什么
- 我该怎么和 TA 沟通
- 如果我这么说，TA 可能怎么回应

所以产品层叫“AI 分身 / 人格档案”，技术层可以叫 `personaSkills`、`contactProfileSkills`。

## 3. 核心功能一：从聊天页生成 AI 分身

### 3.1 入口位置

在用户聊天页面右上角增加一个 AI 操作按钮，建议不直接堆很多按钮，而是做一个 `AI` 下拉菜单。

建议结构：

- `AI 分析`
- `生成 AI 分身`
- `生成回复`
- `关系洞察`
- `人物画像`
- `话题分析`

如果当前页面空间允许，也可以把高频动作露出：

- 主按钮：`生成回复`
- 更多按钮：`AI 更多`
- 更多菜单里包含 `生成 AI 分身`

### 3.2 生成流程

用户点击 `生成 AI 分身` 后，进入一个三步流程：

1. 数据范围确认

   用户选择用于生成分身的聊天范围。

   推荐选项：

   - `全部聊天记录`
   - `最近 1 年`
   - `最近 6 个月`
   - `自定义时间`

2. 生成预览

   系统展示将要生成的内容：

   - 语言风格
   - 性格倾向
   - 常见话题
   - 情绪模式
   - 沟通边界
   - 关系建议
   - 模拟对话规则

3. 确认保存

   用户确认后保存到 `AI 分身库`。

### 3.3 生成结果结构

建议生成的 AI 分身不是一段纯文本，而是一份结构化档案。

核心字段：

```ts
interface AiPersonaProfile {
  id: string
  sessionId: string
  contactName: string
  avatarUrl?: string
  sourceMessageCount: number
  sourceDateRange: {
    startTime: number
    endTime: number
  }
  summary: string
  personality: {
    traits: string[]
    ocean?: {
      openness: number
      conscientiousness: number
      extraversion: number
      agreeableness: number
      neuroticism: number
    }
  }
  communicationStyle: {
    tone: string
    sentencePatterns: string[]
    emojiHabits: string[]
    responseLength: string
    commonPhrases: string[]
  }
  valuesAndMotivations: string[]
  relationshipHints: string[]
  conversationRules: string[]
  promptSkill: string
  createdAt: number
  updatedAt: number
  version: number
}
```

其中 `promptSkill` 是真正用于模拟聊天的核心提示词，可以内部称为 skill。

## 4. 核心功能二：AI 分身库

### 4.1 左侧菜单入口

在左侧菜单加入一级入口：`AI 分身库`。

位置建议放在：

- `聊天` 之后，`朋友圈` 之前；或者
- `聊天分析` 之后，作为分析结果的沉淀入口。

从产品心智看，放在 `聊天` 之后更好，因为它是从聊天关系延展出来的主动功能。

### 4.2 列表页内容

列表页展示当前已生成的 AI 分身。

每个卡片建议展示：

- 头像
- 名称 / 备注名
- 最近更新时间
- 来源聊天条数
- 档案完整度
- 主要标签，比如：`理性`、`慢热`、`高共情`、`高表达欲`
- 操作：`开始对话`、`查看档案`、`重新生成`、`删除`

顶部提供：

- 搜索
- 按更新时间排序
- 按联系人类型筛选：私聊 / 群聊成员 / 群整体
- 空状态引导：`去聊天页生成第一个 AI 分身`

### 4.3 单个分身详情页

详情页分为两个 Tab：

1. `和 TA 对话`

   用户发送一句话，AI 站在该分身的语言风格、价值观、沟通习惯角度回复。

2. `人格档案`

   展示结构化档案：

   - 基本画像
   - 语言习惯
   - 情绪模式
   - 价值观
   - 沟通建议
   - 引用证据
   - 生成信息

## 5. 核心功能三：模拟对话

### 5.1 定位

这个功能不是“真的替对方说话”，而是“基于历史聊天记录模拟一种可能回应”。

界面上建议加安全提示：

> AI 分身基于历史聊天记录生成，只用于沟通演练和关系理解，不代表本人真实想法。

### 5.2 对话模式

建议提供三种模式：

| 模式 | 用户价值 |
| --- | --- |
| 自然聊天 | 像和 TA 聊天一样试探表达 |
| 沟通演练 | 练习如何开口、道歉、解释、邀约 |
| 反应预测 | 输入一句准备发送的话，预测 TA 可能的反应 |

第一版可以只做 `自然聊天`，但数据结构要为后两种预留。

### 5.3 模拟对话 Prompt 策略

系统提示词应包含：

- 只能基于人格档案和聊天证据模拟
- 不要声称自己就是真实联系人
- 保持该联系人的语言风格
- 遇到档案没有的信息要自然表达不确定
- 不输出隐私猜测、控制建议、危险建议
- 可以适度提醒用户这只是模拟

### 5.4 对话历史

建议模拟对话历史独立保存，不写回微信聊天记录。

字段建议：

```ts
interface AiPersonaConversation {
  id: string
  personaId: string
  title: string
  messages: Array<{
    id: string
    role: 'user' | 'assistant'
    content: string
    createdAt: number
  }>
  createdAt: number
  updatedAt: number
}
```

## 6. 更多 AI 功能规划

### 6.1 AI 回复升级

当前聊天页已有 AI 生成回复，但可以升级为更产品化的“回复助手”。

这里需要做一个重要升级：聊天页底部的 `AI 生成回复` 不应该只支持系统预设角色，也应该支持选择用户已经生成的 `AI 分身`。这样用户可以让回复助手站在不同视角里帮自己组织语言。

#### 6.1.1 回复主体体系

这里需要修正一个关键产品判断：聊天页底部回复区不应该让用户主要选择“语气角色”。真实回复时，语气应该由当前聊天语境、对方状态、历史关系、最新消息自动决定，而不是用户手动选一个固定语气。

所以回复区更准确的设计不是 `选择角色`，而是 `选择回复依据` 或 `选择上下文主体`。

回复主体来源分为三类：

| 角色类型 | 示例 | 用途 |
| --- | --- | --- |
| 我的上下文 | 我的表达习惯、当前聊天上下文 | 生成“我应该怎么回” |
| AI 分身 | 某个联系人 AI 分身 | 用来预测 TA 反应、理解 TA、参考 TA 的表达模式 |
| 客服/知识体 | 某个客户画像、产品知识库、服务规范 | 用于客服回复、售前售后、标准化问答 |

界面建议：

- 回复区顶部显示一个主体选择器：`回复依据`
- 默认选中：`当前聊天上下文`
- 如果当前联系人已有 AI 分身，优先显示：`TA 的 AI 分身`
- 如果没有生成，则显示入口：`生成 TA 的 AI 分身`
- 如果启用客服场景，则显示：`客服知识体`
- 点击主体选择器后弹出分组列表：`当前上下文`、`AI 分身`、`客服知识体`

语气不作为主选择项。系统应自动判断：

- 对方是否着急
- 当前关系是否亲密
- 最新消息是询问、抱怨、邀约、催促还是闲聊
- 应该短回、解释、安抚、推进还是收束
- 是否需要更正式、更轻松或更谨慎

只有在生成后，提供少量“微调按钮”：

- `更短`
- `更自然`
- `更礼貌`
- `更直接`
- `降低攻击性`

这些是结果微调，不是生成前的核心入口。

#### 6.1.2 AI 分身在回复区的两种用法

AI 分身进入回复区后，不建议只做一种“替 TA 回复”的模式，而是拆成两个更清晰的模式。

1. `预测 TA 的反应`

   用户输入准备发送的话，AI 分身基于人格档案预测 TA 可能如何理解、可能怎么回应。

   适用场景：

   - 表白前
   - 道歉前
   - 提要求前
   - 解释误会前
   - 商务谈判前

2. `借 TA 的风格表达`

   用户希望参考 TA 的表达方式，生成一段更符合 TA 语言风格的回复。

   适用场景：

   - 想让语气更贴近对方
   - 想知道对方会喜欢什么表达方式
   - 想模仿某个高情商联系人说话

需要注意：产品文案里不要写成“让 TA 替你回复”，而应写成“参考 TA 的风格/预测 TA 的反应”，避免伦理风险。

#### 6.1.3 回复区推荐交互

回复区可以从现在的单 textarea 升级为轻量工作台：

```text
回复助手
以谁的视角生成：我的风格 v
目标：自然回复 v

[生成内容区域]

重新生成   调整语气   复制并打开微信
```

`任务` 下拉建议包含：

- 直接生成回复
- 解读对方意思
- 预测 TA 反应
- 检查这句话是否合适
- 改写我的草稿
- 提炼客服答复
- 生成追问
- 总结当前问题

当选择 `AI 分身` 时，目标里额外展示：

- 预测 TA 反应
- 用 TA 的语言风格改写
- 找出这句话可能踩雷的地方
- 给出更适合 TA 的表达方式

当选择 `客服知识体` 时，任务里额外展示：

- 根据知识库回答
- 安抚用户情绪
- 追问缺失信息
- 给出处理步骤
- 生成标准客服话术
- 判断是否需要人工介入

#### 6.1.4 回复区与 AI 分身库的关系

`AI 分身库` 是资产管理页面，负责查看、更新、删除、模拟聊天。

聊天页底部 `回复助手` 是使用入口，负责在真实上下文里调用这些资产。

两者关系：

- 分身库负责“养成和管理”
- 聊天页负责“即时调用”
- 关系洞察负责“深度解释”
- 回复助手负责“下一句话怎么说”

这个分工能避免页面越来越重，也能让用户建立清晰心智。

建议能力：

- `按我的风格回复`
- `温柔一点`
- `更简短`
- `更坚定`
- `不伤人地拒绝`
- `帮我道歉`
- `帮我推进关系`
- `帮我结束话题`

推荐入口名：`回复助手`。

### 6.2 更深入的 AI 场景扩展

除了用户已经提出的“生成 AI 分身”和“模拟聊天”，还可以继续往真实关系场景里展开。下面这些场景不是都要第一版做，但它们能帮助我们设计更稳定的底层能力。

#### 6.2.1 发消息前：沟通预演

用户经常不是“不知道回什么”，而是担心“这么说会不会出事”。

可做能力：

- `这句话会让 TA 怎么想`
- `这句话哪里容易误解`
- `帮我换一种不冒犯的说法`
- `如果我这样说，TA 可能会冷掉吗`
- `给我 3 个不同强度的版本`

推荐入口：回复助手里的 `预演` 模式。

#### 6.2.2 收到消息后：意图解读

用户收到一句模糊消息时，往往想知道对方真实意图。

可做能力：

- `TA 这句话可能是什么意思`
- `这是敷衍、忙、还是情绪不好`
- `这句话背后有什么未说出口的需求`
- `我应该马上回，还是等等`
- `给出低风险回复`

推荐入口：消息右键菜单 `解读这句话`，或聊天页顶部 `AI 解读`。

#### 6.2.3 关系变冷时：降温诊断

用户能感到关系变了，但不知道从哪里开始看。

可做能力：

- `最近为什么变冷`
- `从哪一天开始变化明显`
- `是不是我哪里没回应好`
- `TA 最近的表达有什么变化`
- `下一步修复建议`

推荐入口：`关系雷达` 和 `关系复盘`。

#### 6.2.4 重要时刻前：策略建议

适合在高风险沟通前给用户做辅助。

可做场景：

- 表白
- 道歉
- 复合
- 分手
- 借钱 / 还钱
- 合作谈判
- 催进度
- 拒绝请求
- 邀约见面
- 久未联系后的重新开口

推荐入口：回复助手目标选择里的 `场景模板`。

#### 6.2.5 长期关系维护：关系记忆

AI 不只是生成内容，还可以帮助用户记住重要信息。

可做能力：

- `TA 最近提到的重要事情`
- `下次聊天可以关心什么`
- `TA 的偏好和雷区`
- `承诺过但还没做的事`
- `纪念日 / 生日 / 重要节点`

推荐入口：联系人页或 AI 分身详情页的 `关系记忆`。

#### 6.2.6 自我成长：我的表达镜子

这个方向能让产品不只是“分析别人”，也能帮助用户理解自己。

可做能力：

- 我是不是经常不接话
- 我是不是只在需要时找别人
- 我常用什么方式表达关心
- 哪些关系里我更主动
- 哪些关系里我更回避
- 我的高频口头禅和情绪模式

推荐入口：`我的表达画像`。

#### 6.2.7 多人关系：群聊策略

群聊不是简单的大号私聊，应该单独设计。

可做能力：

- 这个群里谁是气氛发动机
- 谁是意见领袖
- 谁容易接话
- 这个话题发出去会不会冷场
- 如何让更多人参与
- 在群里怎样发不尴尬

推荐入口：`群聊智能体`。

### 6.3 关系雷达

自动识别近期关系变化。

能力：

- 最近变冷
- 对方回复变慢
- 对方情绪波动增大
- 话题重复度升高
- 互动频率下降
- 关系升温信号

推荐入口名：`关系雷达`。

### 6.4 沟通建议卡

在联系人详情或聊天页右侧展示实时建议：

- 最近适合聊什么
- 哪些话题需要避开
- 对方最近可能关注什么
- 用户近期是否回应不足

推荐入口名：`沟通建议`。

### 6.5 重要关系复盘

选择一个联系人，生成阶段性复盘。

示例：

- `本月我们关系发生了什么变化`
- `这段关系里我做得好的地方`
- `可能让对方不舒服的地方`
- `下一步建议`

推荐入口名：`关系复盘`。

### 6.6 朋友圈 + 聊天联合画像

如果该联系人有朋友圈记录，可以把聊天与朋友圈合并分析。

能力：

- TA 最近关注的话题
- TA 的公开表达和私聊表达是否一致
- 可开启的话题
- 适合评论或互动的方式

推荐入口名：`动态洞察`。

### 6.7 群聊智能体

不仅生成单个联系人分身，也可以生成一个群的“群体画像”。

能力：

- 群氛围模拟
- 群成员角色
- 群聊发言建议
- 哪些人会响应某个话题

推荐入口名：`群聊智能体`。

### 6.8 个人表达镜子

分析用户自己的沟通习惯。

能力：

- 我的表达风格
- 我常见的沟通盲点
- 我在不同关系里的表现差异
- 我是否经常忽略别人
- 我最常使用的情绪表达

推荐入口名：`我的表达画像`。

### 6.9 关系记忆卡

从聊天中自动提取重要信息。

能力：

- 对方生日、纪念日
- 喜好
- 忌讳
- 重要事件
- 承诺事项
- 下次要问候的事情

推荐入口名：`关系记忆`。

## 8. 现有不完美处升级建议

### 8.1 AI 功能散落

现状：

- AI 回复在聊天页底部
- 人物画像 / 关系洞察 / 话题分析是独立页面
- AI 配置在设置里

问题：

- 用户不知道哪些 AI 能力存在
- 生成结果没有沉淀
- 分析和行动之间断裂

建议：

- 建立统一的 `AI 操作中心`
- 聊天页使用统一 `AI` 菜单
- 报告结果允许保存为档案
- AI 配置检测前置，未配置时给出明确引导

### 8.2 生成内容过长，不够产品化

现有 prompt 倾向生成 3000-5000 字长报告，适合深度分析，但不适合高频使用。

建议：

- 第一屏给摘要
- 详细证据可展开
- 输出分为 `结论`、`证据`、`建议`
- 支持重新生成某个模块

### 8.3 缺少任务状态

长聊天记录分析可能耗时较长。

建议：

- 增加生成进度
- 支持后台任务
- 支持取消
- 生成完成后通知
- 失败后可重试

### 8.4 缺少版本管理

联系人画像会随聊天记录变化。

建议：

- 每次重新生成保存版本
- 展示“上次更新时间”
- 支持查看变化：`TA 最近有什么变化`
- 支持一键更新档案

### 8.5 隐私与伦理提示不足

AI 分身容易让用户误以为是真实对方。

建议：

- 首次使用明确提示“模拟不代表本人”
- 不鼓励操控、欺骗、骚扰
- 对敏感推断标注置信度
- 默认本地保存
- 如果调用外部 API，明确提示数据会发送到用户配置的模型服务

```ts
  get: (id: string) => Promise<Result<AiPersonaProfile>>

  delete: (id: string) => Promise<Result<void>>

```

### 9.4 回复助手接口扩展

现有 `ai.generateReply` 需要从“只接收 prompt + role”升级为“支持角色来源和任务目标”。

建议扩展字段：

```ts
interface GenerateReplyPayload {
  sessionId: string
  contextSource: 'current_chat' | 'persona' | 'customer_service_knowledge'
  personaId?: string
  knowledgeBaseId?: string
  goal:
    | 'reply'
    | 'interpret'
    | 'predict_reaction'
    | 'rewrite_draft'
    | 'risk_check'
    | 'customer_service_answer'
    | 'ask_follow_up'
    | 'summarize_issue'
  draftText?: string
  toneOverride?: 'shorter' | 'more_natural' | 'more_polite' | 'more_direct' | 'less_aggressive'
  contextMessages: Array<{ isSend: boolean; content: string; createTime: number }>
}
```

关键规则：

- `contextSource = persona` 时必须传 `personaId`。
- `contextSource = customer_service_knowledge` 时必须传 `knowledgeBaseId`。
- `goal = predict_reaction` 时，输出应包含 `可能反应`、`风险点`、`建议改写`。
- `goal = rewrite_draft` 且选择 AI 分身时，输出应明确这是“参考 TA 的语言风格”，不是“TA 本人的真实回复”。
- `toneOverride` 只用于生成后的轻量微调，不作为主要角色选择。
- 默认不需要用户选择语气，模型应根据上下文自动决定回复语气。
- 如果当前联系人没有 AI 分身，回复区应展示 `生成 TA 的 AI 分身`，而不是隐藏能力。

### 9.5 数据保存

第一版建议保存在本地 `electron-store` 或应用数据目录 JSON 文件，后续再考虑 SQLite。

原因：

- AI 分身数量不会太大
- 结构灵活，方便迭代
- 不污染微信数据库

后续如果要支持搜索、版本、多轮对话历史，再迁移为 SQLite。

## 10. 分期路线图

### V1：AI 分身 MVP

目标：把用户提出的核心功能跑通。

范围：

- 聊天页 `生成 AI 分身`
- AI 分身生成并保存
- 左侧菜单 `AI 分身库`
- 分身列表
- 单个分身模拟聊天
- 聊天页底部 `回复助手` 支持选择 AI 分身作为回复视角
- 支持 `预测 TA 的反应` 和 `用 TA 的语言风格改写` 两个基础目标
- 回复助手的主选择项是 `回复依据/上下文主体`，不是语气角色
- 回复语气由当前语境自动判断，只提供生成后的轻量微调
- 基础删除 / 重新生成

不做：

- 复杂版本对比
- 群聊智能体
- 朋友圈联合分析
- 自动关系雷达
- 让 AI 分身直接代替真实联系人发送消息

### V2：档案产品化

目标：让 AI 分身不只是聊天，还能被查看、更新和复盘。

范围：

- 人格档案详情
- 档案完整度
- 引用证据
- 更新时间
- 更新档案
- 模拟对话模式切换
- 反应预测

### V3：关系智能工作台

目标：把 AI 能力扩展为持续辅助。

范围：

- 关系雷达
- 沟通建议卡
- 关系记忆
- 我的表达画像
- 重要关系复盘

### V4：多源画像

目标：结合更多数据源，让画像更完整。

范围：

- 朋友圈联合画像
- 群聊智能体
- 联系人跨会话聚合
- 周报 / 月报自动生成

## 11. 第一版用户故事

1. 作为用户，我可以在某个联系人聊天页点击 `生成 AI 分身`，让系统基于聊天记录生成 TA 的人格档案。
2. 作为用户，我可以在左侧进入 `AI 分身库`，看到所有已经生成的分身。
3. 作为用户，我可以点击某个分身并和它聊天，用于沟通演练。
4. 作为用户，我可以查看这个分身的生成依据，知道它为什么会这样回答。
5. 作为用户，我可以重新生成或删除某个 AI 分身。
6. 作为用户，我可以在聊天页底部回复助手中选择某个 AI 分身，预测 TA 对我这句话的反应。
7. 作为用户，我可以让回复助手参考某个 AI 分身的语言风格，帮我把话改得更适合这个人。

## 12. 第一版验收标准

- 聊天页能看到 `生成 AI 分身` 入口。
- 点击后能基于当前 session 生成结构化分身。
- 生成结果能本地保存，重启应用后仍存在。
- 左侧菜单能进入 `AI 分身库`。
- 列表页能显示分身数量和基本信息。
- 点击分身能进入模拟聊天。
- 模拟聊天回复明显遵循该联系人档案，而不是普通 AI 助手。
- 聊天页底部回复助手能选择 `当前聊天上下文` 和已生成的 `AI 分身` 作为回复依据。
- 选择 AI 分身后，至少支持 `预测 TA 的反应` 和 `用 TA 的语言风格改写`。
- 回复助手默认根据聊天语境自动判断语气，而不是要求用户先选择“温柔/坚定/简短”等语气。
- 生成后可以提供 `更短`、`更自然`、`更礼貌`、`更直接` 等轻量微调。
- 当前联系人未生成 AI 分身时，回复助手能提示用户先生成，而不是空白或不可用。
- 未配置 AI 模型时，有清晰的设置引导。
- 删除分身不会影响原始聊天记录。
- 所有页面有明确隐私与模拟提示。

## 13. 需要确认的问题

1. 第一版是否只支持私聊联系人，群聊分身放到 V3/V4？
2. `AI 分身库` 是否作为一级菜单，还是放到 `聊天分析` 下面？
3. 分身生成是否默认使用全部聊天记录，还是默认最近一年以降低成本？
4. 模拟对话是否需要保存历史，还是第一版只保留当前会话？
5. 是否允许用户手动编辑人格档案和 promptSkill？
6. 聊天页底部回复助手选择 AI 分身时，默认任务是 `预测 TA 的反应`，还是 `参考 TA 风格改写草稿`？
7. AI 分身能否跨联系人使用？例如在和 A 聊天时，选择 B 的 AI 分身来学习 B 的表达方式。
8. 回复助手是否需要展示“风险提示”和“建议改写”两个独立结果，还是第一版只输出一段可复制文案？
9. 客服场景是否需要第一版接入，还是先只预留 `客服知识体` 数据结构和入口？

## 14. 推荐决策

我的建议是：

- 第一版只做私聊联系人，避免群聊成员身份、上下文归属和多人说话风格造成复杂度爆炸。
- `AI 分身库` 放左侧一级菜单，名字就叫 `AI 分身库`。
- 聊天页按钮叫 `生成 AI 分身`。
- 默认使用最近一年聊天记录，并允许用户切换到全部记录。
- 模拟对话历史第一版可以保存最近 20 轮，后续再做多会话管理。
- 第一版允许查看档案，不允许深度编辑；只提供 `重新生成`，避免用户把产品复杂度拉满。
- 聊天页底部回复助手第一版必须接入 AI 分身，但默认仍选 `当前聊天上下文`，避免用户误以为系统会替对方说话。
- 当前联系人已有 AI 分身时，在回复助手主体选择器里置顶显示 `TA 的 AI 分身`。
- AI 分身跨联系人使用可以保留，但第一版先折叠在 `更多 AI 分身` 里，避免打扰主流程。
- 选择 AI 分身时，默认目标建议是 `预测 TA 的反应`，因为这是最符合“站在 TA 角度”的高价值场景，也最不容易引发冒充风险。
- 不建议把 `温柔版/坚定版/高情商版` 作为第一层角色选择；语气应该由语境自动决定，微调只放在生成结果之后。
- 客服场景可以作为同一套能力的扩展方向：把 `AI 分身` 抽象为 `上下文主体`，未来既可以是联系人分身，也可以是客户画像、产品知识库或客服 SOP。

## 15. 能力契约摘要

### CAPABILITY

用户可以把某个私聊联系人从历史聊天记录中生成一个可保存、可更新、可对话、可在回复助手中调用的 `AI 分身`。这个能力让 WeFlow 从“查看聊天记录”升级为“把关系理解沉淀为可复用智能资产”，并在真实聊天场景中辅助用户做表达预演、风险判断和回复改写。

### CONSTRAINTS

- AI 分身不代表真实联系人本人，只能作为历史记录驱动的模拟对象。
- AI 分身不能自动发送消息，也不能直接写入微信聊天记录。
- 原始聊天数据不被修改，删除 AI 分身不影响原始记录。
- 未配置 AI 模型时，所有生成入口都必须给出配置引导。
- 生成、模拟、回复助手调用都必须显示适度的“模拟不代表本人”提示。
- 第一版默认只支持私聊联系人，群聊智能体后置。
- 回复助手默认依据是 `当前聊天上下文`，AI 分身是可选上下文主体。

### IMPLEMENTATION CONTRACT

用户可见表面：

- 聊天页右上角：`生成 AI 分身`
- 聊天页底部：`回复助手` 主体选择器
- 左侧菜单：`AI 分身库`
- 分身详情页：`和 TA 对话`、`人格档案`

核心状态：

- `未生成`：当前联系人没有 AI 分身，展示生成入口。
- `生成中`：展示进度、允许取消或后台运行。
- `已生成`：可聊天、可用于回复助手、可查看档案。
- `已过期`：新聊天记录超过阈值后提示更新。
- `生成失败`：展示错误原因和重试入口。

核心数据：

- `AiPersonaProfile` 保存人格档案和 promptSkill。
- `AiPersonaConversation` 保存模拟对话历史。
- `GenerateReplyPayload` 支持 `contextSource = persona` 和 `goal = predict_reaction`。

### NON-GOALS

- 第一版不做群聊智能体。
- 第一版不做朋友圈联合画像。
- 第一版不做自动关系雷达。
- 第一版不做复杂版本对比。
- 第一版不允许 AI 分身自动代发消息。
- 第一版不把 AI 分身作为真实联系人的替身来宣传。

### OPEN QUESTIONS

- 回复助手选择 AI 分身时，是否默认展示结构化结果：`可能反应`、`风险点`、`建议改写`？
- 是否允许用户创建和保存多个“我的自定义回复角色”？
- 分身更新阈值如何定义：新消息数量、时间跨度，还是用户手动触发？
- AI 分身是否需要支持导出，方便备份或迁移？

### HANDOFF

当前方案已经可以进入产品确认阶段。确认后建议先实现 V1 MVP：`生成 AI 分身`、`AI 分身库`、`模拟聊天`、`回复助手调用 AI 分身`。技术上优先落 `aiPersonaService`、IPC 合同、前端页面和聊天页回复助手改造。
